# `meticulous try`

Self-serve trial: a developer with only a Meticulous login runs `meticulous try` in their repo,
and their local Claude Code builds the app, records sessions of it and backtests Meticulous
against recently merged PRs, then reports what Meticulous would have caught. No GitHub
integration, CI changes or commits.

## Flow (`start.command.ts`, the default subcommand)

1. `start/confirm-existing-workspace.ts` — an interactive, non-`--headless` re-run over an
   existing `.meticulous-try/` asks whether to continue using it; answering no removes the
   workspace (`worktree/remove-workspace.ts`, refused from inside it) and makes step 3 create
   a brand-new trial project. Non-interactive runs keep reusing it.
2. `start/resolve-try-app.ts` — reuses onboard's app discovery/picker; a non-interactive
   monorepo run leaves the choice to the agent instead of failing.
3. `start/self-onboard-project.ts` — OAuth login (`intent=onboard`, always OAuth, never
   `METICULOUS_API_TOKEN`), then `POST oauth/self-onboard` via `selfOnboard` in
   `@alwaysmeticulous/client`. Idempotent per (user, repo name); also sets the OAuth default
   project. On a fresh start it instead walks `name`, `name-2`, … until the backend reports
   `created: true`. Error kinds (rate limited, project cap, …) map to `CliUserError`s.
4. `start/materialize-try-workspace.ts` — writes the gitignored `.meticulous-try/` workspace:
   the vendored `templates/` (CLAUDE.md, `agents/`, `skills/`), a generated
   `.claude/settings.json` (`start/try-settings.ts`: allowlist incl. the detected package
   manager, denylist for git writes) and `.mcp.json` (onboard's `mergeJsonMcp`). Writes go
   through onboard's `safe-repo-fs` (no symlink escapes).
5. `shared/try-context.ts` — `try-context.json`, mode 0600 (holds the project API token).
6. `start/confirm-launch.ts` — in an interactive, non-`--headless` run, asks before starting
   Claude Code (which takes over the terminal), so the user can read the summary first.
7. `start/launch-try-agent.ts` — launches Claude Code through onboard's `launchOnboardTool`
   with `METICULOUS_API_TOKEN` in its env, so every `meticulous …` command the agent and its
   subagents run is scoped to the trial project. By default (`--lowPriority`) it first lowers
   its own CPU priority, which Claude Code and every install, build and browser it starts
   inherit. `--printOnly` prints a launch command that reads the token from the context file
   instead of printing it, and puts the directory `meticulous` resolves from back on `PATH`:
   under npx that directory is only on this process's `PATH`, so without it the agent's
   `meticulous …` commands would fail in the user's shell.

## The agent's playbook (`templates/`)

Copied into `dist/` by `scripts/copy-try-templates.mjs` and versioned with the CLI.
`CLAUDE.md` defines five phases, each with a skill: build & serve (saves a recipe), record
coverage (crawler + `session-recorder` subagents over CDP), check replays (local `simulate`,
then a cloud baseline plus a second run of the same build that must show no diffs; a code
change that makes replays work is saved with `replay-fix save` and cherry-picked into every
backtest's base and head), backtest PRs (one `pr-backtester`
subagent per PR, launched in parallel with its rank), report (early findings once the first PRs
finish, then the full report, which ends with every likely bug and a direct link to it). App
bugs the agents notice while recording go to `recording-bugs/`, one file each, and are reported
too. Both subagents run on Sonnet (`model:` in their frontmatter).

To keep the machine usable, every install and build runs inside a build slot (`slots/`), and
each slot leases a warm worktree `slot-<n>` shared by every backtester: there are only as many
checkouts and installs as slots, not one per PR. `slot acquire --sha` leases the free slot whose
worktree is closest in history to the commit about to be built (`slots/slot-worktrees.ts`), so
switches and rebuilds stay small; a brand-new worktree gets its `node_modules` copied from an
existing checkout whose install fits the commit (`worktree/seed-node-modules.ts`, copy-on-write
where the filesystem supports it). After a static build, `snapshot-build` renames the output out of the worktree so the slot
can be released while the upload runs; only the head's Agent-swarm launch (which reads the
worktree's source) holds the slot past the build. Checkouts themselves run with one
`checkout.workers` per core, and `prewarm` (run in the background during phase 3's cloud wait)
creates every missing slot worktree in parallel, each briefly claiming its slot
(`tryClaimSlot`) so a backtester never races a half-created worktree. `buildSlots` in try-context.json (about one
per 4 cores and 4 GiB, `--buildSlots` to override) caps how many run at once; waiting
backtesters get slots in rank order.

Apps behind a login go through the `try-app-login` skill before recording: the agent looks for a
dev auth bypass first, then picks a mechanism by where the app keeps its session — browser login
captured by `meticulous try login` (cookies / local storage; also covers SSO and MFA), test
credentials typed into each recording (session storage / IndexedDB), or a token — and pauses once
for the user. Only recording needs the login: replays restore the recorded state.

## Commands the playbook depends on

The templates call `meticulous crawl` (`--headless`, `--nonInteractive`, `--outputFile`, `--storageState`),
`record session` (`--remoteDebuggingPort`, `--headless`, `--storageState`),
`agent upload-build`, `agent trigger-test-run` (`--baseTestRunId`) and `ci agent-test`
(`--deploymentId`, `--baseSha`, `--uploadSource`, `--headTestRunId`). If those flags change,
update `templates/` too; the templates tell the agent to fall back via `--help` when a flag is
rejected.
