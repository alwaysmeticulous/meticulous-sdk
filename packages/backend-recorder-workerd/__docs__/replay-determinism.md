# Replay determinism in the workerd shim

Why `src/virtual-random.ts` and `src/virtual-clock.ts` exist, and what differs from the Node
recorder's copy.

The full reasoning lives with the Node implementation, in
`packages/backend-recorder-js/src/replay/__docs__/replay-determinism.md`. This file covers the
workerd-specific parts and the one rule that keeps the two in step.

## The shared rule

A base replay and a head replay of the same recorded session must render identically, so replay
mode replaces the worker's wall clock and its sources of randomness with deterministic ones.

The distinction to keep in mind when touching either:

**Determinism is not uniqueness, and randomness is used for both.** A timestamp is used for its
_value_, so freezing it at one instant is free. A random draw is very often used for its
_uniqueness_ — ids, keys, nonces, cache busters — so returning one repeated value there does not
make an app deterministic, it breaks it: everything keyed by the id collides.

That is not hypothetical. The fixed-draw phase used to return a single constant, and a dev
server that mints its internal request ids with a `Math.random`-based nanoid produced the same
id for every request. Its in-flight request map is keyed by that id, so requests overwrote each
other — some replies resolved the wrong module, the rest matched nothing and timed out. Every
server render failed and whole test runs were lost.

That phase is gone. Every draw inside a replayed request now comes from the seeded PRNG, from
the first draw, so ids minted from consecutive draws are distinct again.

The phase existed to damp something real: the PRNG's seed is a `callerId` counter handed out in
order of first arrival at a call site, so it is positional, and a PR that routes a new path
through a shared helper can now shift the values another path draws. That trade was made
deliberately — a phase returning one repeated constant was not a workable way to pay for it.

## Keep the two copies identical

`createSeededRandom` is duplicated here rather than imported: this package is published with no
runtime dependencies, and a customer's Worker bundle should not grow to pull in the Node
recorder.

**A session recorded on one runtime and replayed on the other has to draw the same numbers**, so
the two copies must stay byte-for-byte identical. Verify with:

```sh
diff <(sed -n '/^export const createSeededRandom/,/^};/p' packages/backend-recorder-js/src/replay/virtual-random.ts) \
     <(sed -n '/^export const createSeededRandom/,/^};/p' public_packages/backend-recorder-workerd/src/virtual-random.ts)
```

## Differences from the Node version

Both are forced by the runtime, not by choice:

- **Session resolution** comes from the request context (`requestCaptureContext`) rather than a
  session resolver, because workerd's `AsyncLocalStorage` propagates reliably from the inbound
  handler.
- **Only the globals workerd has** are patched — there is no `node:crypto` module to mutate.
- **Reads outside a replayed request fall through to the native generators**, rather than
  returning a constant as the Node recorder does. Module evaluation, recording, and a deployed
  production worker are all untouched. This is also why the shim has no unattributed-draw
  constant: there is no unattributed tier here, and so no equivalent of the Node recorder's
  remaining constant-collision risk.
- **Installation is lazy**, from the replay branch of the request wrapper rather than at module
  scope, so record mode and production workers pay nothing and a bundler cannot tree-shake a
  module-scope side effect away.
