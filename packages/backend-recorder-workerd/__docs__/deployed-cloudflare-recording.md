# Recording a deployed Cloudflare app

How backend recording works when the customer's app is not on `wrangler dev` but **deployed** — `wrangler deploy`, `wrangler pages deploy`, or a preview deployment. Spans two packages: the in-worker shim here, and `@alwaysmeticulous/backend-recorder-sidecar-worker`.

For the local-development flow (a Node sidecar process on loopback), see this package's README and `packages/backend-recorder-js/src/sidecar/`.

## The problem

The shim itself was always cloud-capable: `platform: "neutral"`, no Node dependencies, never in the app's request path. What it lacked was somewhere to send capture events. A deployed Worker has no sidecar process to post to, and the Node sidecar cannot run at the edge — it needs the AWS SDK, an HTTP server and a filesystem.

Three further things had to change before the existing design would survive the edge:

1. **One POST per capture event** was fine over loopback and untenable from a colo: each is a subrequest, and an SSR request making twenty calls would cost twenty round trips.
2. **The capture protocol has no authentication.** It was designed for loopback, so it cannot be exposed publicly.
3. **A Pages project's worker exports `onRequest`**, not `{ fetch }`, so the wrapper did not fit the shape most Pages apps are in.

## The shape

```
customer's Worker / Pages Function
  withMeticulous(...) | withMeticulousPagesFunction(...)
    ├─ patches fetch, fetch-shaped bindings, KV namespaces
    ├─ withMeticulousPostgres patches Query.prototype.handle
    └─ CaptureBuffer batches the request's events; ONE report per request
         env.METICULOUS_SIDECAR.fetch(...)        ← service binding, same colo, no DNS/TLS
                     │
  meticulous-recorder-sidecar  (the customer's own Cloudflare account)
    ├─ fetch: validate → hand to the Durable Object → 204     ← thin: waitUntil is blocked
    └─ MeticulousRecorderSession (SQLite-backed Durable Object)
         ├─ persist the batch, arm a 5s alarm
         └─ alarm: SpanBuilder → serializeSpan → SigV4 PUT to S3
              s3://user-events-v3/<token12>/BE_<iso>_<id>/{metadata.json,1,2,…}
```

From there it is the existing pipeline: the S3 write triggers ingestion, which correlates backend spans to frontend sessions by the `meticulous.frontend_session_id` span attribute.

## Decisions worth knowing

**A service binding, not a public endpoint.** The protocol carries no auth, so the sidecar is only reachable through the binding and its shipped wrangler config sets `workers_dev = false`. A binding call also never leaves the colo, so it costs no DNS or TLS.

**The binding beats the URL var when both are set.** A stale `METICULOUS_SIDECAR_URL` in a `.dev.vars` travels with an image; a binding can only exist because someone added it to _this_ deployment's wrangler config.

**The sidecar binding is excluded from recording by identity, not by name.** It is Fetcher-shaped and sits on `env`, so the binding patch would otherwise discover it and record every report — an infinite regress. `installBindingPatch` takes `skipInstances` for exactly this, so a customer who renames it or passes `options.sidecarBinding` is still covered.

**The shim mints the trace and server-span ids** (`CorrelatedEvent` in `protocol.ts`). Span assembly is then stateless, which matters because the sidecar's Durable Object can be evicted between two batches of one request — a sidecar that had to remember `requestId → traceId` would split that request's trace. `SpanBuilder` keeps its old per-`requestId` map only as a fallback for a shim that predates the fields.

**One report per request, drained by `CaptureBuffer.close()`.** A response body is only captured once its clone has drained, which happens _after_ the handler returns — so producers register with `track()` and the single `waitUntil` promise awaits them before sending. Events added after `close()` (work the app itself queued in `waitUntil`) are sent individually rather than dropped.

**Fan-in, not one session per frontend session.** One Durable Object holds spans from many frontend sessions, exactly as the Node sidecar does. Ingestion (`fetchBackendSpans`) lists `<token12>/BE_` over a ±10-minute window and filters by span attribute, so the number of S3 folders is what that scan costs — a session per frontend session would have made it grow with concurrency. Sharding via `METICULOUS_SIDECAR_SHARDS` is free for the same reason: nothing downstream keys off which object a span passed through.

**The 30-chunk / 10-minute rollover is deliberately unchanged** from `SessionSpanExporter`. It pairs with ingestion's `BUFFER_MS = 600_000` window: a `BE_<iso>` timestamp is the session's _start_, so a folder spanning much more than ten minutes falls outside the window of the frontend sessions at its tail.

**Batches live in Durable Object storage, one key each.** An alarm survives eviction; instance fields do not. One key per batch rather than one growing array because a single capture event can carry two 256 KB bodies — fine against a SQLite-backed object's 2 MB key+value limit, and impossible against the 128 KiB limit of the older key-value backing store. (Hence `new_sqlite_classes` in the shipped migration.)

A report is not bounded by that 2 MB, though: `CaptureBuffer` flushes once _past_ its threshold, so the event that crossed it is still in the batch, and the estimate it used counts only body text. `splitToFitValueLimit` therefore splits a report across as many keys as it needs. The batch keys and the sequence counter go in one multi-key `put`, which is atomic — written separately, an eviction between them would leave the counter behind and the next report would overwrite these events under the same key. The alarm is armed before the write, so the worst case is a wake-up with nothing to drain rather than durable events with nothing scheduled to upload them.

**Chunk state is written before the batches are dropped.** A crash in between re-uploads a chunk, which is harmless — ingestion reads spans, and a repeated span matches the same way — whereas losing one is a gap in the recording.

**Abandonment is a back-off, not an ending.** Three consecutive upload failures abandon the session, as in the Node exporter — but there the flag dies with the process, and here it would outlive the outage in the object's storage. So it carries `abandonedAtMs`, and the next report after five minutes starts a fresh session. Without that, one bad five minutes of S3 would silently end recording for the whole deployment until someone wiped the object by hand.

## Shared code, and why it moved

Three things had to be reachable from both a Worker and Node, so they are defined here and re-exported by `packages/backend-recorder-js`:

| What                                           | Here                                      | Re-exported from                                                   |
| ---------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------ |
| Span attribute names, technology tags          | `spans/attributes.ts`                     | `src/constants.ts`                                                 |
| `ReadableSpan`, `serializeSpan`, `SpanBuilder` | `spans/`                                  | `src/exporters/span-serializer.ts`, `src/sidecar/span-builder.ts`  |
| postgres.js record contract, error capture     | `postgres/capture.ts`, `error-capture.ts` | `src/postgres-js-capture-shared.ts`, `src/error-capture-shared.ts` |

The reason is always the same one `serializeKvCaptureFields` already had: a recording made through one surface has to be byte-identical to one made through the other, or it cannot be replayed by the machinery built for it. A customer's deployed sidecar drifting from this repo's replay stores is a silent failure, so there is one implementation.

What stayed in `backend-recorder-js` is everything replay-only: match-key building (it needs a synchronous SHA-256), result and error reconstruction, and the OTel-`Span` writers.

## postgres.js in a Worker

`withMeticulousPostgres` exists because a Worker is a single bundle: `postgres` was inlined at build time and never passes through a module loader, so the require hooks the Node recorder uses can never fire. It reaches the shared `Query.prototype` through a throwaway `sql.unsafe` query — free, because postgres.js queries are lazy — and patches `handle`, wrapping each query's own `resolve`/`reject` to capture the outcome.

It is **record-only**. The captured attributes are exactly what `PostgresJsMockStore` reads, so a Worker recording replays through the existing Node path; a workerd container replaying one would reach the real database (see the note in `packages/webapp-backend/src/replay/cloud-replay/__docs__/backend-replay.md`).

## Known gaps

- **Streamed responses capture truncated.** The inbound event is reported when the handler returns, before a streamed body drains, and outbound bodies cap at 256 KB. An app whose main endpoints are SSE will not record them faithfully.
- **The `inferred` span-attachment heuristic gets riskier with concurrency.** Ingestion attaches unstamped spans by time window, which with several people on one deployment can attach another user's SSR spans into a session. It is gated on the project's admin-only `enableBackendSpanTimestampMatching` setting, so a shared deployment can opt out — at the cost of recording no SSR render for the session-starting navigation unless the backend mints the session id itself. The principled fix — a first-party session cookie the Worker can read on document navigations — is not implemented; the recorder sets no cookie today.
- **No sampling or kill switch.** Every request through a wrapped handler with a configured sidecar is recorded.
- **R2, queues and JS-RPC bindings are still uncaptured** by the shim, though `withMeticulousCloudflareEnv` covers them on the Node side.
